# Twin SF1000 (4×8 lamp on GPIO5) design

**Date:** 2026-08-29  
**Status:** approved (plan Sec2 lock)

## Problem

Clone SF1000 lives on **GPIO23** as `light.dsc_hub_sf1000_dimmer`. The 4×8 tent has only a photoperiod **window** proxy. Twin / Climate / Mission often treat the clone light as the main tent light (REL-P0-3). Firmware already reserves **GPIO5** for a 4×8 PWM module.

## Goals

1. Ship a distinct ESPHome light named **Twin SF1000** on GPIO5 PWM.
2. Expected entity: `light.dsc_hub_twin_sf1000_dimmer` (slug from name; confirm after compile).
3. SPA Twin / 4×8 light UI prefer the twin entity when available; window binary remains honest fallback.
4. Clone GPIO23 lamp and its history keys stay clone-owned.

## Non-goals

- Removing the clone SF1000
- Claiming live brightness without PWM hardware wired on GPIO5 (FOLLOWUPS honesty)
- Independent HVAC rooms

## Design

1. Add monochromatic LEDC/PWM output on **GPIO5** in [`firmware/v4/dsc-hub-v4_0.yaml`](../../../firmware/v4/dsc-hub-v4_0.yaml).
2. Light name **`Twin SF1000`**; keep **`SF1000 Dimmer`** on GPIO23 unchanged.
3. Wire photoperiod / Twin shafts / Mission glow for 4×8 to twin entity when state is available; else `binary_sensor` window proxy.
4. Brain history + SPA entity maps gain a twin key; do not retarget clone history onto twin.
5. FOLLOWUPS: PWM module must be present for live brightness; software path ships first; hub OTA when authorized.

## Acceptance

- Entity present after hub OTA (or compile proves entity id).
- SPA Twin uses twin for 4×8; clone dimmer still controls 2×4.
- No blank / wrong-tent light bar on Twin.
